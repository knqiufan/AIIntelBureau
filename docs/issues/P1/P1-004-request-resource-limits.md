# P1-004：HTTP、LLM 与 SSE 缺少资源配额

- 状态：Closed（2026-07-23）
- 分类：可用性 / 成本防护
- 优先级：P1

## 已证实证据

- `backend/app/services.py:225-235` 的耳语限流仅存在进程内字典，按 case+角色计数，
  不覆盖创建案件、审问、公开、SSE 或跨进程部署。
- `backend/app/main.py:211-223` 的 SSE 连接无限循环，未设置连接上限、空闲上限或
  每调用者配额。
- `ask()` 可触发向量检索和可选 LLM 调用；`_smoke` 在启用时会批量执行这些操作。
- `nginx.conf` 未声明请求体上限、连接/请求限速或突发策略。

## 影响

攻击者或误操作可制造案件、长期占用 SSE、刷检索和 LLM 请求，导致费用、数据库容量、
线程池和现场大屏体验失控。单进程内存限流在重启或水平扩容后会自动失效。

## 修复方案

1. 以调用者和 IP 为维度设计令牌桶：创建、写入、审问、发布、SSE 分别设预算与突发值。
2. 使用 Redis/数据库等共享存储实现跨 worker 一致限流；本地开发可使用明确标记的内存实现。
3. 在 Nginx 设置 `client_max_body_size`、连接/请求限速和慢客户端策略；为 SSE 设专用限制。
4. 为 LLM/embedding 设置并发池、请求超时、熔断和每日成本预算；错误降级不得无限重试。

## 验收标准

- 单一调用者无法超过各端点预算，响应为可识别的 429 且不泄露内部信息。
- 两个 API 副本共享同一配额；重启后不会重置生产调用者的额度。
- 压测验证合法的大屏连接数量内稳定，超额 SSE 被优雅拒绝/关闭。
- 仪表盘可见被限流次数、活跃 SSE、LLM 并发、超时和预算消耗。

## 依赖

先完成 P0-003 的生产身份/网络边界，才能定义可信调用者。限流键不得直接记录原始口令、
问题或私有内容。

## 修复记录

SQLite 共享窗口计数实现 HTTP、耳语和模型预算；LLM 有并发槽，SSE 有连接配额与寿命，Nginx 施加边缘限速。每空间写入前检查容量，拒绝返回脱敏 429。复测：容量、会话和多实例发布测试。
