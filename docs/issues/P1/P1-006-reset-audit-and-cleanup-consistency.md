# P1-006：重置、审计与远端清理语义不一致

- 状态：Closed（2026-07-23）
- 分类：数据生命周期 / 审计正确性
- 优先级：P1

## 已证实证据

- `backend/app/services.py:178-193` reset 逐卡删除远端记忆、更新 case 并追加
  `case.reset`，但不删除或标记既有 `memory.published` 事件。
- `services.py:328-357` 的公开审计从 case 的全部事件中扫描 `memory.published`，
  因此 reset 后仍会显示已不存在的公开卡。
- `clear_ephemeral_data()` 和 CLI 先后删除远端/本地；任一远端删除失败时没有可恢复的
  删除状态、重试清单或一致性报告。

## 影响

公开审计可能展示“幽灵公开记录”，与当前公告板不一致。重置或自动清理中断后，本地账本、
远端向量库和 UI 可能分别宣称不同状态，既误导演示，也使删除证明不足。

## 修复方案

1. 定义 reset 语义：保留历史但标记为已重置并按 epoch 过滤，或归档事件后在当前视图排除。
2. 为删除引入持久化任务状态、幂等删除标识和可重试补偿；禁止在远端未确认前宣称完成。
3. 将审计 API 明确为“当前状态”或“历史事件”，分别提供不同 DTO，避免混合语义。
4. 对 ephemeral 清理输出脱敏的删除汇总和失败任务，不自动丢弃可重试线索。

## 验收标准

- reset 后的当前公告板、stage 快照和“当前审计”一致；历史审计有明确 epoch/已重置标识。
- 注入远端删除失败时，系统保留可恢复任务，重试后达到本地与远端一致。
- 清理 CLI 在无健康远端时不误报成功；所有状态转换有测试。

## 观测

记录每次 reset/清理的 case、epoch、目标数、成功数、失败类型与补偿状态；不记录卡片正文。
该项依赖 P1-009 的保留期策略和 P1-010 的告警能力。

## 修复记录

reset 进入 `resetting` 并持久化逐卡清理任务，远端删除失败不宣布完成。epoch 将历史审计与当前公告视图区分；ephemeral 与保留期清理均为远端先删、本地后删。复测：reset/audit 测试。
