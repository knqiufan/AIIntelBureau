# P1-008：SSE 断线从零重放并放大快照请求

- 状态：Closed（2026-07-23）
- 分类：实时同步 / 性能可靠性
- 优先级：P1

## 已证实证据

- `backend/app/main.py:211-223` 支持 `after_event_id` 游标并为每个事件发送 `id`。
- `web/src/api.ts:88-97` 建连总是使用默认 `after_event_id=0`，没有维护最后事件 ID；
  `EventSource` 自动重连后的请求也不会把客户端状态带入 URL。
- `web/src/ui/App.tsx:102-110` 每收到一个事件即调用 `refreshSnapshot()`。
- `docs/adr/ADR-005-sse.md` 描述游标重放，但客户端实现没有兑现该契约。

## 影响

一次网络/Nginx 断线后，服务端会重发案件全部历史事件；客户端对每一条再次拉快照，
长时间演示时会造成重复引导状态、N 次请求、数据库读取尖峰和 UI 卡顿。

## 修复方案

1. 客户端保存已成功处理的最大 event ID；连接和重连时显式传入 `after_event_id`。
2. 服务端支持标准 `Last-Event-ID` 并规定其与 query 参数的优先级、非法值和事件保留期。
3. 事件处理仅更新必要的本地状态；使用去抖/合并方式刷新快照，或让事件直接携带安全投影。
4. 为历史截断定义 `resync_required` 响应：客户端只拉一次最新快照并重建游标。

## 验收标准

- 模拟断线后，只传输断线期间漏掉的事件；历史事件不重复触发 snapshot。
- 1000 条历史事件后重连的 HTTP 快照请求数量有明确上限。
- 事件 ID、事件保留和全量重同步的契约写入 ADR、OpenAPI/前端类型和测试。
- P1-003 的心跳/代理超时测试与本 issue 的游标测试同时通过。

## 观测

记录连接数、每连接重放事件数、resync 次数、快照刷新次数和断开原因。指标标签不得含
case ID 等高基数值或任何私有正文。

## 修复记录

前端以 case/角色隔离的安全事件 ID 游标重连，并持久化引导进度；事件快照刷新合并至 120ms，stage 有低频恢复轮询。服务端 heartbeat/连接配额与 Nginx SSE 超时共同防止断连从零重放。复测：Playwright 刷新恢复和大屏 E2E。
