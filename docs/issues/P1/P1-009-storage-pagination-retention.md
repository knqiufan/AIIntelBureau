# P1-009：记忆分页、数据保留和容量边界未定义

- 状态：Closed（2026-07-23）
- 分类：数据正确性 / 生命周期
- 优先级：P1

## 已证实证据

- `backend/app/memory.py:177-181` 的生产 gateway 对 `get_all()` 固定 `limit=100`；
  `get_private()` 又基于这份截断列表查找。
- `services.py:178-186` reset 依赖 `list_space()`，超过上限的卡可能不会被删除。
- 默认 `DEMO_DATA_RETENTION=persistent`（`settings.py:38-39`），创建案件、自由耳语、
  事件账本和远端记忆都没有容量、TTL 或每 case 上限。

## 影响

长期运行、异常重试或大量耳语后，snapshot 不完整、发布找不到旧卡、reset 清不干净。
持久化数据还会持续增长，增加成本、检索噪声和隐私暴露面。

## 修复方案

1. 明确数据模型上限：每 case、角色、公开板和事件的最大卡数/字节数与保留期。
2. 实现可靠分页或按 ID 精确读取，禁止使用前 100 条列表作为删除/授权依据。
3. 为持久模式提供 TTL、归档、配额拒绝和管理员清理；为 ephemeral 模式提供可验证清理。
4. 建立存储迁移与索引策略，避免事件全表扫描和无限增长。

## 验收标准

- 单空间超过 100 条后，读取、发布、reset、清理仍覆盖全部匹配卡，不出现孤儿。
- 超过定义配额时返回可操作错误，不写入部分数据。
- 保留任务和手工清理都产生脱敏汇总，可验证远端与本地删除完成。
- 压测报告说明目标容量下的检索、快照和重置性能。

## 待验证

PowerMem 对 `get_all` 的分页 API、远端删除上限和一致性语义需要在真实版本中验证。
在验证完成前，不能假设增加单个 `limit` 就能解决所有清理问题。

## 修复记录

已核实 PowerMem 的 `get_all(limit, offset)` 接口并实现分页去重，读取/发布/reset/清理不再依赖前 100 条。每空间有容量上限；persistent 默认七天保留，过期 case 远端优先删除。复测：SDK gateway 与容量测试。
